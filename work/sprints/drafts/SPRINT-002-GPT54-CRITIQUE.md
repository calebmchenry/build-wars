# Combined Critique

## `SPRINT-002-GPT56SOL-DRAFT`
- **Strengths:** This is the stronger execution draft. The early `CatalogRecord.source` -> `provenance` migration is the right sequencing choice because the current repo still has a singular source model in [catalog.ts](/Users/calebmchenry/code/build-wars/src/domain/catalog.ts:7), and the draft explicitly removes that ambiguity up front ([GPT56SOL draft](/Users/calebmchenry/code/build-wars/work/sprints/drafts/SPRINT-002-GPT56SOL-DRAFT.md:34)). The phase order, explicit ticket chain, phase acceptance criteria, and detailed DoD make it much closer to an actually runnable sprint.
- **Weaknesses:** The one sequencing issue is its claim that `BW-0102` and `BW-0103` can run in parallel ([GPT56SOL draft](/Users/calebmchenry/code/build-wars/work/sprints/drafts/SPRINT-002-GPT56SOL-DRAFT.md:200)). Parts of `BW-0103`, especially `scripts/data/README.md` and the artifact lineage wording, depend on finalized contract names and manifest semantics from `BW-0102`, so the draft needs either a narrower parallel boundary or an explicit contract-freeze handoff.
- **Risk gaps:** Its risk table is strong, but it under-specifies governance risk. The draft requires reviewer metadata and bounded exceptions, yet it never defines who is authorized to accept risk, approve ambiguous-source use, or bless committed generated-artifact exceptions; that leaves an operational dependency unresolved even if the documentation is complete.
- **Missing edge cases:** It covers mixed-field provenance well, but it should explicitly test invalid or overlapping JSON Pointer claims, claims targeting nonexistent fields after migration, and single fields backed by multiple upstream sources. It also should verify that manual overrides reference the superseded claim or prior value, not just that a rationale exists.
- **Definition of Done completeness:** Very strong overall. The remaining DoD gap is not breadth but handoff precision: it should explicitly require that the finalized `BW-0102` vocabulary is the one used by `BW-0103`/`BW-0104`, and it should require named authority for release exceptions rather than only recording that an exception happened.

## `SPRINT-002-GPT55-DRAFT`
- **Strengths:** This draft is clear on scope control, keeps the domain boundary clean, and does a better job than GPT56SOL at spelling out execution bookkeeping artifacts such as the final sprint file, ledger row, and a fallback ticket-burn test path. Its high-level dependency diagram is concise and directionally correct.
- **Weaknesses:** The largest flaw is the additive-contract stance ([GPT55 draft](/Users/calebmchenry/code/build-wars/work/sprints/drafts/SPRINT-002-GPT55-DRAFT.md:45)). Because the repo still uses a singular `source` field in [catalog.ts](/Users/calebmchenry/code/build-wars/src/domain/catalog.ts:7) and [foundation.ts](/Users/calebmchenry/code/build-wars/test/fixtures/foundation.ts:24), deferring the migration pushes the hardest schema break into `EPIC-02` and risks two competing provenance models. It also incorrectly pulls planning artifact creation into sprint execution by requiring `plan-EPIC-01-result.json` to be written during Phase 1 and in the DoD ([GPT55 draft](/Users/calebmchenry/code/build-wars/work/sprints/drafts/SPRINT-002-GPT55-DRAFT.md:184), [GPT55 draft](/Users/calebmchenry/code/build-wars/work/sprints/drafts/SPRINT-002-GPT55-DRAFT.md:323)); that reverses dependency order instead of respecting it.
- **Risk gaps:** The risk section omits the most important migration and release-gating risks: dual truth between `source` and provenance, accepted-risk turning into a blanket bypass, and freshness/retrieval metadata drift. It also does not address approval authority for ambiguous classifications, which matters because the draft allows explicit acceptance of critical findings.
- **Missing edge cases:** The draft never pins field provenance to RFC 6901 JSON Pointer semantics, does not define whole-record scope, and does not call out non-waivable cases like digest mismatch or unreadable artifacts. It also misses exact-path allowlist guardrails, mixed-source single-field cases, migration of current fixtures/consumers, and a separate `error` severity between `critical` and `warning`.
- **Definition of Done completeness:** It is stronger on administrative traceability than on technical closure. The DoD does not require eliminating the old singular source model, proving artifact lineage/digest preservation, documenting non-waivable QA cases, or distinguishing app-consumption gates from public-release gates, so it would allow the sprint to close with core policy mechanics still underspecified.

## Comparison And Merge Recommendations
- Use `SPRINT-002-GPT56SOL-DRAFT` as the base. It has the better dependency model, the better verification strategy, and the more complete Definition of Done.
- Pull in only two ideas from `SPRINT-002-GPT55-DRAFT`: an explicit check that `work/sprints/SPRINT-002.md` and `work/sprints/ledger.tsv` are finalized consistently, and the conditional fallback to `python3 -m unittest scripts/test_ticket_burn.py` if `npm run verify` does not actually cover ticket-burn tests.
- Do not merge GPT55’s additive-contract guidance, planning-manifest creation, or three-level severity model. Those choices either defer the critical schema break or weaken release gating.
- Tighten GPT56SOL’s sequence to `BW-0101 -> BW-0102 -> BW-0103 -> BW-0104 -> BW-0105`, or keep its partial parallelism only if `BW-0103` is explicitly split so contract-dependent documentation waits for `BW-0102` to freeze names and shapes.
- Add two merge-time requirements that neither draft finishes cleanly: explicit reviewer/exception authority, and explicit tests for invalid, overlapping, and multi-source field provenance claims.
